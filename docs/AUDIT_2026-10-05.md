# Audit aplikasi backup Microsoft 365 - 2026-10-05

## Ruang lingkup dan metode

Audit baca-saja pada kode `spo-backup-final`, image yang berjalan di lima container,
konfigurasi yang terpasang, endpoint lokal, Redis, log worker, dan metadata/file lokal.
Tidak ada backup, restore, penghapusan, maupun panggilan tulis ke Microsoft 365.
Tidak ada task backup/download aktif saat pemeriksaan (`/api/task/active` mengembalikan null).
Karena itu penyebab tampilan progress saat task aktif disimpulkan dari jalur kode,
bukan direproduksi langsung di browser.

## Temuan prioritas kritis

1. **Identitas backup site tidak unik; hasil 614/614 tidak membuktikan 614 salinan site.**
   `BackupEngine.backup_site` membentuk folder dari `name.replace(" ", "_")`
   (`app/backup_engine.py:570-581`), dan `ManifestManager._path` juga memakai nama
   (`app/backup_engine.py:180-190`). Konfigurasi aktif memiliki 26 nama folder yang
   dipakai lebih dari satu URL allowlist (67 entri URL). Contoh: dua `CEO Office Team`,
   empat `Marketing`, dan sepuluh `Test`. Backup site berikutnya dapat menimpa file
   dengan path relatif sama dan selalu mengganti `_backup_metadata.json` site sebelumnya.
   Folder `data/backupm365` berisi 577 folder, 575 metadata site, 563 URL allowlist
   unik yang terbukti oleh metadata, 51 URL allowlist yang tidak terbukti, dan 12
   metadata URL di luar allowlist. Ini **bukan bukti 51 site pasti hilang**: banyak
   yang bertabrakan identitas; tetapi klaim semua 614 terverifikasi saat ini tidak
   didukung bukti lokal. `Customer Excellence` adalah contoh nyata: metadata folder
   menunjuk `sites/cex`, bukan `sites/CustomerExcellence`.

2. **Unduhan file tidak memverifikasi panjang akhir.** Setelah `iter_content`,
   `_download` langsung `os.replace(tmp, dest)` lalu mencatat sukses
   (`app/backup_engine.py:298-395`, image aktif memiliki logika sama). Tidak ada
   cek ukuran akhir terhadap `item.size`/`Content-Range`, tidak ada checksum, dan
   respons 206 tidak divalidasi bahwa rentang dimulai di offset `.tmp`. File `.tmp`
   yang panjangnya >= size_hint malah langsung dipromosikan. Jalur OneDrive/Outlook/
   Teams (`app/workloads/base.py:250-315`) memiliki kekurangan sejenis. Akibatnya
   file terpotong, kelebihan byte, atau resume yang salah dapat dinyatakan berhasil.
   Rekonsiliasi 61.648 entri manifest dari backup `20260728_111338`, setelah path
   lama dipetakan ke `backupm365`, menemukan 56.384 ukuran cocok dan 5.264 berbeda
   (5.198 lebih besar, 66 lebih kecil). Ini adalah **sinyal untuk verifikasi**, bukan
   bukti pasti korupsi: manifest dapat usang dan folder pernah digabung/ditimpa.

3. **Sukses site dan sukses restore dapat menyembunyikan file gagal.** Di backup,
   exception per file hanya masuk `stats.errors`, lalu site tetap menambah
   `successful_sites` (`app/backup_engine.py:647-695`). Run terakhir tercatat
   `614/614` tetapi `_workload_manifest.json` berstatus `partial`; log task memuat
   setidaknya sepuluh contoh file dengan HTTP 401. `_backup_runtime.json` untuk
   run yang sama malah bertuliskan `success` (`app/backup_engine.py:748-757`).
   Pada restore, `_upload_file` menangkap error per file, tetapi site tetap
   `targets_processed`; `RestoreManagerV2.execute` menandai `completed` selama
   ada target berhasil dan tidak ada error bertanda `Fatal:`
   (`app/restore/sharepoint.py:137-160,226-252`,
   `app/restore_manager_v2.py:275-301`). Ini berisiko membuat backup yang belum
   lengkap diperlakukan sebagai dasar penghapusan sumber.

4. **Kode deployment dan konfigurasi workspace berbeda.** Hash `main.py`,
   `dashboard.html`, `backup_engine.py`, `workloads/base.py`, dan `tasks.py` di
   image aktif tidak sama dengan workspace; `restore_manager_v2.py` sama. Image
   aktif bertanggal awal Agustus. Config aktif `config/config.json` memiliki 630
   site dan jadwal disabled, sedangkan `spo-backup-final/config.json` berisi 13 site
   dan jadwal enabled. Compose memasang config aktif dari `../config/config.json`
   (`spo-backup-final/docker-compose.yml:14-17`). Rebuild atau penyalinan config
   tanpa rekonsiliasi dapat mengubah cakupan backup dan menghapus optimasi runtime.

## Progress bar dan status

5. **Panel backup bergantung pada satu key Redis yang berumur 24 jam.** Worker
   menulis `spo:current_backup_task` sekali dengan TTL 86.400 detik
   (`app/tasks.py:219-221`; image aktif `app/tasks.py:356`). Endpoint cepat
   `/api/task/active` hanya membaca key ini; fallback inspeksi Celery tersedia
   hanya pada jalur non-fast (`app/main.py:221-304,460-556,982-1000`). Dashboard
   menyembunyikan panel segera bila endpoint mengembalikan null
   (`app/templates/dashboard.html:278-299`). Backup 614 site terakhir berjalan
   84.276 detik, sekitar 23 jam 25 menit: sangat dekat TTL. Bila run melampaui
   24 jam, Redis kehilangan key sementara worker masih berjalan, sehingga panel
   hilang setelah reload/navigasi. Redis saat audit sehat dan key task memang
   tidak ada, karena saat ini tidak ada task aktif; pemicu spesifik pada sesi
   pengguna belum bisa dipastikan tanpa reproduksi langsung.

6. **Progress total backup tidak stabil selama scan.** `files_total` dan
   `bytes_total` ditambah satu per satu saat traversal Graph
   (`app/backup_engine.py:594-610`). Persentase dapat mundur/100% terlalu awal
   saat file baru ditemukan. Dashboard memakai `overall_pct` tersebut sebagai
   lebar bar (`app/templates/dashboard.html:303-355`). UI dashboard memonitor
   backup, sedangkan restore v2 memakai daftar job tersendiri; restore tidak
   akan muncul di panel backup.

7. **Persentase restore dihitung dari keberhasilan sejauh ini, bukan total kerja.**
   `processed/(processed+failed)` dibatasi 99% (`app/restore_manager_v2.py:242-255`).
   Setelah satu file berhasil dan nol gagal, bar langsung 99% meski ribuan file
   masih antre; kegagalan kemudian justru menurunkan persentase. Status failed
   akhir dipaksa 100%. UI mem-poll setiap empat detik
   (`app/templates/restore_v2.html:679-771`). Perlu tahap enumerasi dan total
   file/byte, lalu progress monotonik berbasis selesai/total.

## Kinerja dan kematangan fitur

8. **Publish progress dan log di workspace terlalu sering.** Callback backup
   menulis snapshot Redis dan Celery state pada setiap event; file selesai juga
   menulis satu log per file (`app/tasks.py:224-245`). Image aktif sudah memiliki
   throttle 0,75 detik/25 file/16 MiB dan log per 50 file, tetapi perubahan ini
   belum ada di workspace. Rebuild dari workspace dapat mengembalikan overhead
   tinggi, terutama puluhan ribu file.

9. **Manifest dan resume mahal dan kurang andal.** Manifest JSON site disimpan
   ulang setelah setiap 25 perubahan atau 5 detik (`app/backup_engine.py:219-244`).
   Pada site besar, serialisasi seluruh map dan penulisan non-atomik berulang
   menambah I/O; jika proses mati di tengah tulis, `ManifestManager.load` dapat
   gagal. Banyak manifest menyimpan path absolut ke direktori backup lama. Dari
   229.017 entri yang dipindai, 210.331 path aslinya tidak ada, namun banyak
   menunjuk ke data yang sudah dipindah. Jangan memakai angka ini sebagai jumlah
   file hilang. Reuse file juga bergantung pada eTag/waktu tanpa validasi ukuran
   atau hash lokal (`app/backup_engine.py:605-640`).

10. **Antrean dan histori mempunyai batas operasional.** `OperationQueue.list`
    membaca posisi dengan scan ulang list untuk setiap item
    (`app/operation_queue.py:46-79`), sehingga biaya naik kuadratik. Redis
    dikonfigurasi `allkeys-lru` dengan batas 512 MiB
    (`docker-compose.yml:42-43`), sehingga kunci kontrol/progress/histori dapat
    ter-evict saat tekanan memori. Saat audit Redis hanya memakai 1,91 MiB,
    jadi ini risiko desain, bukan penyebab yang teramati sekarang. Job restore
    disimpan dalam 100 ID terakhir (`app/restore_manager_v2.py:97-100`) dan
    status final backup Celery kedaluwarsa setelah 24 jam (`app/tasks.py:135`).

11. **Restore file besar dan mode merge belum memeriksa isi target.** Upload
    session mengirim chunk 5 MiB tanpa checkpoint offset/validasi respons akhir
    (`app/restore/sharepoint.py:256-282`). Mode merge melewati file jika path
    target ada, tanpa perbandingan ukuran/hash (`app/restore/sharepoint.py:226-244`).
    Restore Teams hanya mengekspor HTML/JSON/TXT lokal, bukan memulihkan pesan
    ke Teams (`app/restore/teams.py:1-62,225-255`). UI perlu menyatakan batas
    ini jelas sebelum operasi.

12. **API administrasi terbuka pada port host.** Tidak ditemukan autentikasi
    aplikasi pada route dashboard, config, restore, dan delete backup. Compose
    memetakan port 5050 ke semua interface (`docker-compose.yml:11-12`), dan
    GET `/` serta `/api/v2/restore/jobs` mengembalikan HTTP 200 tanpa login
    dari localhost. Jika tidak ada kontrol reverse proxy/firewall di luar
    container, siapa pun yang dapat menjangkau port ini dapat memakai API
    administrasi. `/api/browse` juga memeriksa prefix string path, bukan
    `Path.is_relative_to` (`app/main.py:1237-1265`). Lingkup akses jaringan
    eksternal belum diuji.

13. **Cakupan pengujian otomatis tidak ditemukan.** Tidak ada suite `test_*.py`,
    `*_test.py`, atau `pytest.ini` di source aplikasi. Perubahan pada unduhan,
    progress, resume, collision nama, dan restore memerlukan uji kontrak dengan
    HTTP respons terpotong, Range yang salah, nama site duplikat, Redis TTL,
    dan file gagal di tengah site.

## Prioritas patch yang disarankan

1. Bekukan penggunaan label `614/614` sebagai bukti aman untuk penghapusan;
   rekonsiliasi per URL dan per file dari allowlist, termasuk 51 URL yang belum
   terbukti serta 5.264 mismatch ukuran. Simpan laporan immutable per run.
2. Ganti key backup dengan identitas site URL/Graph site ID dan nama folder aman,
   migrasikan backup lama tanpa menimpa data. Perbaiki marker selesai hanya bila
   semua file terverifikasi, dan bedakan `success`, `partial`, `failed` konsisten.
3. Tambahkan verifikasi ukuran/Range setelah unduhan, retry URL download yang
   kedaluwarsa lewat Graph, serta checksum bila tersedia. Restore harus
   memverifikasi target setelah upload dan menghitung kegagalan per file.
4. Sediakan status job persisten dengan heartbeat dan sumber progress tunggal;
   dashboard dan halaman restore membaca status yang sama. Hitung progress
   setelah enumerasi total file/byte dan tampilkan fase scan/transfer/verify.
5. Rekonsiliasi image aktif, source, dan config sebelum deploy; simpan tag image
   immutable beserta commit/version di UI/log. Tambahkan autentikasi/otorisasi
   API dan tes regresi untuk jalur utama.

## Batas kesimpulan

Audit ini tidak membandingkan checksum file dengan SharePoint/Microsoft 365
karena sumbernya telah mengalami penghapusan/restore, dan tidak menjalankan
Graph scan baru. Perbedaan ukuran lokal versus manifest dapat berasal dari
manifest lama, penggabungan folder, atau file yang berubah; semuanya memerlukan
rekonsiliasi berdasarkan site ID dan item ID sebelum dinyatakan rusak/hilang.
Tidak ada patch kode atau deployment dalam audit ini.
